# 本地账号隔离修复

## 已确认的问题

原业务仓库和聊天仓库是进程内单例，都连接 `citygo_app.db`。
账号切换只切换登录凭证，没有切换这些仓库或销毁全局业务 ViewModel。
因此不同账号可以读到同一份行程、聊天、宠物、日记和本地收藏；旧账号异步任务也可能继续影响界面。

## 修复后的边界

- 每个登录手机号经 SHA-256 生成稳定的本机分区，数据库名称为 `citygo_account_<分区>.db`，不含明文手机号。
- 行程、聊天、宠物、本地收藏、日记、浏览历史和本地帖子随账号分库；当前城市按账号分键。主题设置仍按设备共享。
- Repository 在创建时固定数据库，不会因之后切换账号而把旧写入写进新账号数据库。
- Activity 保留一个业务 ViewModelStore 容器。会话身份变更时清理旧 Store，取消旧业务任务，并从目标账号数据库创建新 ViewModel。
- Token 更新不改变数据文件；会话 generation 会变化，旧请求结果失效。A→B→A 也不会使最初 A 的请求重新有效。
- 共享鉴权客户端在创建 Call 时捕获会话，发送前和收到响应后检查版本。切换身份取消排队及执行中的请求。
- 单图、多图穿搭客户端复用受会话保护的流式客户端；流式响应不使用 BODY 日志或业务 JSON 预读，避免阻塞 SSE。
- 401 事件绑定原始会话；消费时再次校验，避免旧账号的迟到响应让新账号退出。
- 资料回写、账号落盘和退出操作增加会话检查；身份切换清理保存的 Tab 返回栈。
- 登录时建立最小身份后仍需继续获取资料，因此不直接销毁登录页面的 AuthViewModel。

当前本机身份以手机号为键，与现有账号列表一致；未来支持换绑手机号时，应迁移为后端不可变 userId。
这里的哈希用于分区与避免文件名泄露手机号，不是数据库加密。

## 旧数据处理

**不删除、不覆盖旧 `citygo_app.db` 及其 SQLite 辅助文件，也不自动认领旧数据。**

旧库从未记录账号归属，无法可靠判断其中的行程和聊天属于谁。
升级后各账号首次进入的新分区可能为空；旧共享数据仍在原文件里，需确认归属后才能安全导入。
原共享城市设置同样保留，但不自动赋给所有账号。
本次没有修改 Room 实体、版本 8 的 schema 或历史迁移链，也不使用破坏式迁移。
